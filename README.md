# Referral (REFR) and ReferralHook

This contribution contains the fixed-supply ERC-20, the native-ETH referral hook,
vendored dependencies, Foundry tests and generated ABI exports. Solidity is pinned
to **0.8.26**, with Cancun EVM, optimizer 200 runs and `bytecode_hash = "none"`.
No FFI, filesystem cheatcode permissions, network RPC, environment variables or
submodules are needed by the tests. The compiler and Foundry are verifier-provided
tooling; all Solidity dependencies are ordinary files under `lib/`.

```sh
forge build
forge test
forge fmt --check
# Also verifies extended fuzz cases, dependency checksums and ABI freshness:
bash check.sh
```

| Hook fee | Constant 20 bps, no protocol share |
| Pool | currency0 = native ETH (`address(0)`), currency1 = deployed REFR |

Neither contract has an owner, admin, public mint, setter, pause, upgrade, sweep,
delegatecall or selfdestruct. REFR mints its entire supply once in its constructor.
The hook validates all 14 permission bits in its constructor with
`Hooks.validateHookPermissions`. Disabled callback selectors are not implemented;
the manager never calls them. Initialization and liquidity operations are ungated.
Local tests pass a genuinely deployed PoolManager as the single constructor
argument; they do not relocate manager code or bypass hook address validation.

CREATE2 mining must use the **actual factory CREATE2 deployer address** and
`keccak256(ReferralHook.creationCode ++ abi.encode(poolManager))`. Match
`uint160(predictedAddress) & 0x3fff == 0x00cc`. Any change to compiler settings,
source, constructor argument or factory address requires mining again. A bounded
working miner is in `test/helpers/HookMiner.sol`; no salt or deployed address from
the test is a Sepolia deployment parameter.

## Factory rehearsal and manifest assumptions

The supplied workflow does not contain a manifest price, seed amount or factory
source. `test/helpers/LaunchFactory.sol` reproduces its stated lifecycle: create
the token and receive all supply, deploy the hook at a mined address, initialize,
then add token-only liquidity within one manager unlock. It uses these explicit
parameters for the later manifest author to adopt or reconcile:

| Rehearsal field | Value |
| --- | --- |
| Initial sqrtPriceX96 | `2505036234966386302045715536678303` |
| Initial tick / seed upper tick | `207240` |
| Seed lower tick | `-887220` |
| REFR seed budget | `800000000000000000000000000` (800 million REFR) |
| Seed liquidity | `floor(seedBudget * 2^96 / (sqrtUpper - sqrtLower))` |
| Starting native ETH | 0 |

Both tokens use 18 decimals, so the starting token1/token0 price is approximately
one billion REFR per ETH. At the upper boundary the seed requires only REFR.
Liquidity is rounded down; the small remainder stays with the factory until the
fixture distributes remaining tokens to its caller for testing. That distribution
is test funding, not a specification of the live factory's allocation or custody.

The rehearsal verifies the initial price, no ETH funding, correct first buys in
both exact-input and exact-output modes, and claim backing after the first buy.
An independently produced `launch.json` must match these values or the rehearsal
must be rerun with its actual values. No manifest is generated by this assignment.

## Referral and fee rules

Valid referral data is exactly one canonical 32-byte ABI-encoded address. Zero,
`tx.origin`, the hook and its PoolManager are invalid. Empty data, other lengths,
and noncanonical address words pay no fee and update no referral statistics.
`sender` is the router, not authenticated user identity, and is not used for
authorization. There is no router allowlist.

Let `A = abs(amountSpecified)`, `P = abs(poolSwapDelta.amount0())`, and
`R = floor(ETH-leg * 20 / 10000)`. Amounts and rewards are in wei. Positive hook
deltas mean the hook receives funds. The pool's normal LP fee remains separate.

| Mode | ETH-leg fee base | Hook delta | Pool's specified amount | Caller receives/pays |
| --- | --- | --- | --- | --- |
| Exact-input buy | A | beforeSwap specified +R | ETH input A − R | Pays exactly A ETH |
| Exact-output sell | A | beforeSwap specified +R | ETH output A + R | Receives exactly A ETH |
| Exact-output buy | P | afterSwap unspecified +R | Requested REFR output | Pays P + R ETH |
| Exact-input sell | P | afterSwap unspecified +R | Requested REFR input | Receives P − R ETH |

In `afterSwap`, the hook checks the pool's specified delta, less the before fee
when applicable, against `amountSpecified`. A partial fill reverts with
`PartialFill`, including swaps without a referrer. v4 wraps callback errors in
`WrappedError`. Reverting unwinds all balances, minted claims and events. Pools
whose currency0 is not native ETH receive zero deltas and no hook restrictions,
events or state updates, including no partial-fill restriction.

Zero-rounded rewards remain zero. A valid dust referral still records its fee
base, increments its count once, and emits `Referred(..., 0)`. No claims are minted
for zero rewards. The hook supports every native-ETH pool using its address;
there is no immutable token argument or first-pool registration race.

## Settlement, views and events

Swaps mint the reward as ERC-6909 native-ETH claims (currency ID 0) **to the hook**.
Minting creates a manager debit canceled by the hook's returned positive fee
delta. Neither swap callback takes or sends ETH, so an initially ETH-less pool
can execute its first buy before the router settles its input.

`claim()` zeros the caller's whole balance, starts a manager unlock, and pays that
caller via the hook's manager-only `unlockCallback`. The callback burns the same
amount of ETH claims before `take(nativeETH, referrer, amount)`. It never trusts a
caller-supplied payout recipient. A zero balance returns 0 without unlocking or
emitting an event. A rejecting receiver reverts only its claim and restores the
debt and claims; other users can still swap and claim. Positive claims must begin
while PoolManager is locked. Reentering a zeroed claim pays zero; trying to claim
newly accrued rewards during an existing unlock reverts atomically.

| API | Meaning |
| --- | --- |
| `balanceOf(address)` | Current total claimable ETH across supported pools |
| `referredVolume(address)` | Lifetime total ETH fee base in wei |
| `referralCount(address)` | Lifetime valid referred swap count, including dust |
| `poolReferrals(PoolId,address)` | Pool-specific lifetime `(volume,count,earned)`; earned is cumulative, not claimable |
| `claim()` | Pays caller's entire balance; returns the paid amount |
| `Referred(address indexed referrer, bytes32 indexed poolId, uint256 ethLeg, uint256 reward)` | One valid referral, emitted in the fee-taking callback |
| `Claimed(address indexed referrer, uint256 amount)` | Successful nonzero withdrawal |

Pool statistics are keyed by PoolId. The required address-only views and claim
balance aggregate them across pools; no pending swap state is shared between
pools or callbacks. PoolId is the v4 hash of the entire pool key. Events allow
indexing without an unbounded on-chain referrer or pool list. ABIs are in
`docs/abi/REFR.json` and `docs/abi/ReferralHook.json` (plain JSON arrays).

## Accounting invariant and limitations

For every sequence of supported swaps and claims, the sum of referrer balances
equals `PoolManager.balanceOf(hook, 0)`. The stateful invariant tests cover two
pools, four referrers, all four swap modes, invalid referrals and interleaved
claims, with independent expected accounting derived from manager swap events.
Every generated action must succeed (`fail_on_revert = true`), and each sequence
ends by withdrawing all remaining debts. Additional tests cover partial-fill
rollback, failed payouts, repeat claims and nested swaps during a payout.

**Unsolicited-claim qualification:** absolute equality against arbitrary external
actions cannot be enforced by a recipient of v4 ERC-6909 claims. Anyone can fund
an unlock and call `PoolManager.mint(hook, 0, amount)`, or transfer existing claims
to the hook, without invoking it. This creates surplus without referral debt.
`test/ClaimDonations.t.sol` reproduces that exact sequence and verifies existing
claims remain payable. With such donations the solvency relation is **claims >=
sum of debts**; the ordinary-operation equality invariant assumes no unsolicited
claims. Surplus is inaccessible because there is deliberately no sweep or admin.
Raw ETH/token gifts likewise do not create referral balances. This protocol-level
limit is an explicit review finding, not an assertion of unconditional equality.

The `tx.origin` self-referral check is weak: a second wallet defeats it, and the
0.2% returns to the swapper's second wallet (no net gain or loss of that fee,
excluding gas, pool fees and price effects). Smart accounts and relayers also make
`tx.origin` an imperfect identity signal. It is never used as authorization.
`hookData` is unauthenticated: a swapper can choose whom it pays. Counts and volumes
are therefore not proof of independent human referrals and can be inflated by
self-directed activity or dust.

## Operational handoff

The manifest contributor owns `launch.json`; an independent contributor reviews
the accepted source and manifest, including constructor and policy conflicts.
This local test suite and self-check are not that independent adversarial review.
Services own source publication, signed artifact linkage, attestation, admission,
authorized factory deployment, and subsequent frontend work. Later service
receipts are not prerequisites of this source contribution.

Before deployment, services must reconcile the manifest price/seed parameters,
verify the exact Sepolia manager and factory behavior, mine against the final
creation code, and run their live-chain rehearsal. This suite uses a real local
v4-core manager, not a Sepolia fork or a claim of deployed-chain verification.
The frontend must use the actual deployed addresses and complete pool key, read
prices and events, encode referral data, apply slippage limits, and request claims
from the connected referrer's wallet. No contract administrator can correct a
bad deployment or rescue a permanently rejecting referrer.

Vendored source revisions and individual SHA-256 hashes are recorded in
`docs/dependencies.json`. Third-party license files are retained beside each
dependency. The delivered contracts and tests are MIT licensed.
